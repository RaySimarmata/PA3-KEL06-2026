## 3.2.6.1 Gambaran Umum Workflow

Workflow Agent-Based Report Assistant adalah arsitektur sistem yang menggunakan AI Agent sebagai orchestrator utama untuk mengelola seluruh proses pembuatan laporan berkualitas. Sistem ini menggabungkan:

- **RAG Pipeline** (Retrieval-Augmented Generation) untuk context-aware generation
- **LLM Multi-Provider** untuk resiliensi dan optimasi biaya
- **Document Intelligence** untuk OCR dan vision processing
- **Quality Evaluation** untuk continuous improvement

Keuntungan menggunakan agent-based dibanding sequence diagram:
- ✅ Menunjukkan **intelligence & decision making** (bukan hanya linear flow)
- ✅ Menangani **exception handling** secara natural
- ✅ Mendukung **multi-turn conversation** dengan adaptive behavior
- ✅ **Scalable** untuk kompleksitas sistem yang tinggi
- ✅ Lebih mudah di-**maintain & evolve**

### 3.2.6.2.2 Agent Orchestration Layer

**Deskripsi:**  
Brain dari sistem yang membuat keputusan intelligent tentang flow mana yang harus dijalankan.

**Komponen Utama: AIAgentService**

#### 3.2.6.2.2.1 Intent Parser
**Fungsi:** Memahami apa yang benar-benar diinginkan user.

**Proses:**
```
Input: "Analisis kinerja GKM prodi TRPL semester ganjil"
           ↓
Parse intent: 
  - Task Type: LAPORAN TRIWULAN
  - Focus: PRODI TRPL (filter)
  - Semester: GANJIL (filter)
  - Aspects: KEPATUHAN + KUALITAS (multi-aspect)
           ↓
Output: Structured intent object
{
  task: "analyze_report",
  period: "triwulan_1_2026",
  filters: {prodi: "TRPL", semester: 1},
  aspects: ["rps_compliance", "learning_quality"],
  requires_rag: true,
  requires_ocr: (ada file gambar),
  confidence: 0.95
}
```

#### 3.2.6.2.2.2 Route Decision Engine
**Fungsi:** Memutuskan pendekatan apa yang optimal untuk request.

**Decision Points:**

1. **Apakah perlu RAG?**
   - YA: Jika ada konteks dari dokumen/data
   - TIDAK: Jika hanya computational task
   - CONDITIONAL: Tergantung complexity

2. **Apakah perlu OCR?**
   - YA: Jika ada file gambar
   - TIDAK: Jika hanya text/structured data

3. **Apakah multi-turn?**
   - Conversation history ada?
   - Gunakan context dari turn sebelumnya?

4. **AI Provider mana?**
   - Vision task? → Claude (Claude 3.5 Sonnet)
   - Generation task? → OpenAI (gpt-4o-mini)
   - Quality-critical? → Ensemble multiple providers

**Pseudocode:**
```php
if (has_images) {
    use_ocr_pipeline();
    use_claude_ai();  // Claude punya vision capability
} 

if (requires_context) {
    retrieve_rag_context();
    augment_prompt();
}

if (is_multi_turn) {
    load_conversation_history();
    merge_with_current_query();
}

select_best_provider_for_task();
```

#### 3.2.6.2.2.3 Pipeline Coordinator
**Fungsi:** Mengatur orchestration dari multiple services.

**Pipeline yang diatur:**

```
┌─ Spark Pipeline (big data processing)
│  └─ Aggregate GKM monthly data untuk context
│
├─ RAG Pipeline (context retrieval)
│  ├─ Chunking: Split documents into chunks
│  ├─ Embedding: Vectorize chunks
│  ├─ Retrieval: Find most relevant chunks
│  └─ Augmentation: Add to prompt
│
├─ OCR Pipeline (image processing)
│  ├─ Image validation (relevance check)
│  ├─ Text extraction (PaddleOCR)
│  ├─ Chunking extracted text
│  └─ Vector indexing
│
└─ LLM Pipeline (text generation)
   ├─ Multi-turn history management
   ├─ Provider selection & fallback
   ├─ Generation with augmented context
   └─ Quality evaluation (RAGAS)
```

#### 3.2.6.2.2.4 Conversation State Manager
**Fungsi:** Manage multi-turn conversation context.

**State Tracking:**
```
Turn 1:
  Input: "Analisis kinerja GKM TRPL"
  Output: Draft laporan
  Context_stored: {
    filters: {prodi: "TRPL", semester: 1},
    rag_results: [...],
    ai_response: "...",
    timestamp: now()
  }
  
Turn 2:
  Input: "Fokus ke RPS saja"
  Previous_context: ↑ (reuse from Turn 1)
  Merge: Previous context + new focus
  
Turn 3:
  Input: "Tambah rekomendasi"
  Conversation_history: [Turn 1, Turn 2, Turn 3]
  Context_window: ~4000 tokens (trimmed history)
  Generate: Enhanced response
```

#### 3.2.6.2.2.5 Error Handling & Recovery
**Fungsi:** Manage exceptions dan fallback gracefully.

**Error Scenarios:**

1. **Provider Failure**
   - OpenAI timeout → Try Gemini
   - Gemini quota exceeded → Try Groq
   - All failed → Return error message

2. **RAG Failure**
   - No relevant context → Generate without RAG
   - Low similarity → Expand threshold
   - Timeout → Use cached results

3. **OCR Failure**
   - PaddleOCR fails → Claude Vision fallback
   - Image irrelevant → Skip and warn user
   - Both fail → Continue without image context

**Recovery Strategy:**
```
try {
    execute_primary_path();
} catch (ProviderException $e) {
    log_error($e);
    execute_fallback_provider();
} catch (RagException $e) {
    log_warning($e);
    generate_without_context();
} finally {
    save_conversation_state();
}
```

```
[4] AGGREGATE
    ├─ GroupBy prodi, matakuliah, tingkat
```

#### 3.2.6.2.3.2 RAG Context Retrieval

**Fungsi:**  
Ambil konteks relevan dari vector store untuk augment prompt.

**Step-by-step Process:**

**Step 1: Query Embedding**
```
User Query: "Analisis kinerja TRPL semester ganjil"
           ↓
EmbeddingService.generateEmbedding(query)
           ↓
Query Vector: [0.234, 0.512, -0.123, ..., 0.456]
              (1536 dimensions)
```

**Step 2: Semantic Search**
```
Search dalam DocumentChunk table:
  WHERE source_type IN ['laporan_gjm', 'monitoring_data']
  AND similarity(chunk_embedding, query_vector) >= 0.7
           ↓
Top-K retrieval: K=10 most similar chunks
```

**Step 3: Result Re-ranking**
```
Results: [
  {chunk: "RPS compliance TRPL 85%", similarity: 0.92},
  {chunk: "Learning quality index 3.2", similarity: 0.88},
  {chunk: "Dosen performance TRPL", similarity: 0.85},
  ...
]
           ↓
Re-rank by:
  - Relevance score (similarity)
  - Recency (lebih baru prioritas)
  - Diversity (avoid redundant chunks)
           ↓
Final: Top 5 most useful chunks
```

**Step 4: Context Assembly**
```
Retrieved chunks
           ↓
Build context object: {
  overview: "Compiled chunk texts",
  statistics: {
    total_chunks: 5,
    avg_similarity: 0.88,
    coverage: "RPS + Learning + Dosen"
  },
  metadata: {
    source_types: ["monitoring", "analysis"],
    time_range: "2026-01 to 2026-03",
    prodi_covered: ["TRPL", "TI"]
  }
}
```

**Teknologi:**
- Service: `RAGRetrievalService`
- Vector DB: MySQL DocumentChunk table
- Similarity: Cosine similarity
- Threshold: 0.7 (configurable)

#### 3.2.6.2.3.3 OCR & Image Processing

**Fungsi:**  
Extract text dan context dari gambar yang di-upload.

**Pipeline:**

```
[1] FILE UPLOAD
    └─ User upload: IMG_20260615.jpg (screenshot/foto)
    
[2] IMAGE VALIDATION
    ├─ Check: Apakah relevant untuk laporan?
    ├─ Method: Claude Vision API (image understanding)
    └─ Decision: ACCEPT atau REJECT
    
[3] OCR TEXT EXTRACTION
    ├─ Engine: PaddleOCR (Python service)
    ├─ Output: Extracted text + confidence score
    └─ Fallback: Claude Vision API (if PaddleOCR fails)
    
[4] TEXT PROCESSING
    ├─ Clean extracted text
    ├─ Normalize whitespace
    ├─ Fix encoding issues
    └─ Deduplication
    
[5] CHUNKING & INDEXING
    ├─ Split into 300-word chunks
    ├─ Generate embeddings
    ├─ Store to DocumentChunk
    └─ Metadata: source=ocr, image_id=xxx
    
[6] RAG INTEGRATION
    └─ Include OCR chunks dalam RAG retrieval
       (untuk subsequent AI prompts)
```

**Teknologi:**
- OCR Engine: PaddleOCR (Python service)
- Vision API: Claude Vision (validation)
- Service: `OCRService`, `ImageContentValidationService`
- Storage: DocumentChunk table (MySQL)

**Contoh Input/Output:**
```
Input: Foto screenshot dashboard GKM
       (1200x800px, PNG)
       
OCR Output:
"Dashboard Monitoring GKM
TRPL Semester Ganjil 2026
RPS Compliance: 85%

Result: Chunks indexed untuk RAG
```

### 3.2.6.2.4 LLM & AI Generation Layer

**Deskripsi:**  
Layer yang generate actual report content menggunakan LLM.

#### 3.2.6.2.4.1 Intelligent Provider Selection

**Fungsi:**  
Choose best AI provider based on task requirements.

**Selection Criteria:**

```
Task Type Analysis:
  ├─ Chat/Conversation?
  │  └─ Use OpenAI (gpt-4o-mini) PRIMARY
  │     └─ Fallback: Gemini 1.5 Flash
  │
  ├─ Vision/Image Analysis?
  │  └─ Use Claude (Claude 3.5 Sonnet) PRIMARY
  │     └─ Fallback: Groq (llama-3.3-70b)
  │
  ├─ Generation/Content?
  │  └─ Use Claude PRIMARY
  │     └─ Fallback: OpenAI → Groq
  │
  └─ Cost-critical?
     └─ Use Gemini (free tier)
        └─ Fallback: Groq (cheap)
```

**Provider Configuration:**

| Provider | Cost | Speed | Quality | Free Tier |
|----------|------|-------|---------|-----------|
| OpenAI gpt-4o-mini | $ | Medium | Excellent | ❌ |
| Gemini 1.5 Flash | Free | Fast | Good | ✅ (1500/day) |
| Claude 3.5 Sonnet | $$ | Slow | Excellent | ❌ |
| Groq llama-3.3-70b | $ | Very Fast | Good | ✅ |
| OpenRouter | Free | Medium | Good | ✅ (6 models) |

**Decision Tree:**
```
if (has_images || needs_vision) {
    primary_provider = "Claude";
    fallback_provider = "Groq";
} elseif (is_chat) {
    primary_provider = "OpenAI";
    fallback_provider = "Gemini";
} elseif (cost_critical) {
    primary_provider = "Gemini";
    fallback_provider = "Groq";
} else {
    primary_provider = "Claude";
    fallback_provider = "OpenAI";
}

// Check provider health
if (primary_provider.is_healthy()) {
    use_provider(primary_provider);
} else if (fallback_provider.is_healthy()) {
    use_provider(fallback_provider);
} else {
    return error_response();
}
```

#### 3.2.6.2.4.2 Multi-Provider Fallback Chain

**Fungsi:**  
Handle provider failures gracefully dengan automatic fallback.

**Provider Chain Architecture:**

```
UnifiedAIService (Main Router)
├─ PRIMARY: OpenAI gpt-4o-mini
│  ├─ Timeout: 30 seconds
│  ├─ Retry: 3 times dengan exponential backoff
│  ├─ Rate limit handling: 429 status
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Fallback 1
│
├─ FALLBACK 1: Gemini 1.5 Flash
│  ├─ Free quota: 1500 requests/day
│  ├─ Retry: 2 times
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Fallback 2
│
└─ FALLBACK 2: Error Response
   └─ Message: "Semua layanan AI tidak tersedia"

ClaudeAIService (Alternative Chain)
├─ PRIMARY: Anthropic Claude 3.5 Sonnet
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Fallback 1
│
├─ FALLBACK 1: Groq llama-3.3-70b
│  ├─ Speed: ~100 tokens/sec
│  ├─ Free: Yes (some limits)
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Fallback 2
│
├─ FALLBACK 2: OpenRouter (6 free models rotating)
│  ├─ Models: meta-llama, google/gemma, microsoft/phi
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Fallback 3
│
├─ FALLBACK 3: HuggingFace Inference API
│  └─ SUCCESS? Return ✅
│       └─ FAIL? Go to Error
│
└─ ERROR: Return error message
```

**Fallback Flow Example:**
```
Request: Generate laporan triwulan untuk TRPL
           ↓
Try OpenAI gpt-4o-mini
└─ 429 Rate Limit Error (quota exceeded)
           ↓
Try Gemini 1.5 Flash
└─ 200 OK ✅ Response generated
           ↓
Return response to user

```

### 3.2.6.2.5 Quality Evaluation & Feedback Layer

**Deskripsi:**  
Layer yang evaluate response quality dan decide apakah butuh refinement.

#### 3.2.6.2.5.1 RAGAS Evaluation Framework

**Fungsi:**  
Measure 5 quality metrics untuk AI-generated response.

**5 Metrics:**

| Metric | Formula | Threshold | Interpretation |
|--------|---------|-----------|-----------------|
| **Faithfulness** | Claims in response matched to context | >0.8 | Response berdasarkan fact, bukan hallucination |
| **Answer Relevancy** | Similarity(response, query) | >0.85 | Response menjawab pertanyaan user |
| **Context Precision** | % context chunks actually used | >0.75 | Context yang diberikan useful |
| **Context Recall** | Coverage of response vs context | >0.8 | Semua informasi penting tercover |
| **Context Relevancy** | Relevance of context chunks | >0.8 | Context yang diambil benar-benar relevan |

**Evaluation Process:**

```
Input:
  - user_query: "Analisis TRPL"
  - ai_response: "Program Studi TRPL menunjukkan..."
  - context_chunks: [5 retrieved chunks]
         ↓
RAGASEvaluationService.quickEvaluate()
         ↓
Calculate 5 metrics:
  [1] Faithfulness: 0.87 ✅
  [2] Answer Relevancy: 0.91 ✅
  [3] Context Precision: 0.82 ✅
  [4] Context Recall: 0.78 ✅
  [5] Context Relevancy: 0.85 ✅
         ↓
Overall Score: (0.87 + 0.91 + 0.82 + 0.78 + 0.85) / 5 = 0.846
         ↓
Decision:
  If Overall > 0.85: ACCEPT ✅
  If 0.7 < Overall < 0.85: ACCEPT + WARNING ⚠️
  If Overall < 0.7: RETRY or ALERT ❌
```

**Save Metrics:**
```
Store to laporan_gjm table:
{
  ragas_faithfulness: 0.87,
  ragas_answer_relevancy: 0.91,
  ragas_context_precision: 0.82,
  ragas_context_recall: 0.78,
  ragas_overall_score: 0.846,
  evaluated_at: now()
}
```

#### 3.2.6.2.5.2 Quality-Based Decision Making

**Fungsi:**  
Decide next action berdasarkan quality metrics.

**Decision Logic:**

```
Overall Score = 0.846

IF score >= 0.85:
  ├─ Decision: ACCEPT
  ├─ Action: Save draft, show to user
  └─ Status: READY FOR DOWNLOAD

ELSEIF 0.7 < score < 0.85:
  ├─ Decision: ACCEPT + WARN
  ├─ Action: Save draft, show warning
  ├─ Warning: "Response quality medium, recheck"
  └─ Status: READY (but needs review)

ELSEIF score < 0.7:
  ├─ Decision: RETRY or MANUAL
  ├─ Actions:
  │  ├─ Option 1: Auto-retry dengan different provider
  │  ├─ Option 2: Show to user for manual refinement
  │  └─ Option 3: Use fallback template
  └─ Status: NEEDS REFINEMENT
```

```
Pre-defined Sections:
  1. Cover + Header

```

**Processing:**

```
[1] LOAD TEMPLATE

[2] PARSE AI CONTENT
    ├─ Split response into sections
    ├─ Extract text dari setiap section
    ├─ Clean markdown formatting
    └─ Escape special characters
    
[3] INSERT PLACEHOLDERS
```

### 3.2.6.11.1 GKM Kuesioner Monitoring Workflow

**Skenario:** Dosen upload file kuesioner Excel, agent analyze & generate insights

**Poin-demi-Poin:**

1. **Initiation Phase**
   - GKM staff membuka halaman "Upload Kuesioner"
   - Menu: GKM → Monitoring Kuesioner → Upload Baru
   - Controller: `GKM/MonitoringKuesioneController@showUpload()`
   
2. **File Input & Validation**
   - File input: Excel (.xlsx, .xls) atau CSV
   - Size limit: 10MB (configurable)
   - Validation:
     - Check file type (whitelist: xlsx, xls, csv)
     - Check file size
     - Check content (header row exists?)
     - Scan for malware (optional)
   - Rejected file: Return error message
   - Accepted file: Proceed to processing
   
3. **Initial Processing**
   - Store file: `storage/uploads/kuesioner/{date}/{filename}`
   - Generate: File metadata (size, rows, columns)
   - Create: Database record in `monitoring_kuesioner` table
   - Status: "UPLOADED" (not yet processed)
   
4. **Queue Job Decision**
   - File row count < 1000? → Process synchronously (fast)
   - File row count >= 1000? → Queue to job (async)
   - Rationale: Large files need Spark, shouldn't block HTTP
   
5. **Data Ingestion (Spark Pipeline)**
   - **If File ≥ 1000 rows:**
     - Queue job: `ProcessLargeKuesioneFile`
     - User sees: "Processing queued. Check back in 5 minutes"
     - Backend: Job runs `spark_kuesioner.py`
     - Steps:
       - Read Excel via SparkSQL
       - Parse matakuliah, prodi, dosen
       - Normalize data (case-insensitive, trim whitespace)
       - Handle missing values
       - Convert Likert scale (e.g., 1=Kurang → 4-point scale)
   
   - **If File < 1000 rows:**
     - Process synchronously in-request
     - Same Spark steps but return immediately
     - User sees: Processing spinner (max 30 sec timeout)
   
6. **Data Transformation (Spark)**
   - Extract structured data:
     - Matakuliah: Map to matakuliah_id
     - Prodi: Normalize prodi code
     - Dosen: Extract from title (format: "nama - dosen")
     - Questions: Identify question columns (Q1, Q2, ..., Q20)
   
   - Transform data types:
     - Response column: Cast to integer (1-4 or 1-5)
     - Date: Parse YYYY-MM-DD format
     - Status: Map text to enum (Sangat Baik, Baik, etc.)
   
   - Aggregate by grouping:
     - GroupBy: matakuliah_id, prodi, dosen
     - Calculate: mean, stddev, count for each question
     - Categorize: If mean >= 3.5 → "Sangat Baik", etc.
   
7. **Data Storage**
   - Output file location: `hdfs://data/processed/kuesioner/{batch_id}`
   - Store to MongoDB: collection `hasil_analisis_lengkap`
     - Document structure:
       ```json
       {
         "_id": ObjectId,
         "batch_id": "batch_20260615_001",
         "matakuliah_id": 42,
         "prodi": "TRPL",
         "dosen_id": 15,
         "semesterAjaranId": 1,
         "summary": {
           "total_responden": 45,
           "rata_rata_kepuasan": 3.6,
           "status": "Sangat Baik"
         },
         "pertanyaan_detail": [
           {
             "nomor": 1,
             "pertanyaan": "Kualitas materi pembelajaran",
             "rata_rata": 3.8,
             "kategori": "Sangat Baik"
           },
           ...
         ],
         "processed_at": ISODate("2026-06-15T10:30:00Z"),
         "_schema_version": 2
       }
       ```
     - Also to MySQL: `monitoring_kuesioner` table
   
8. **Notification & User Feedback**
   - If sync (< 1000 rows):
     - Show: Success message + summary statistics
     - Display: Table dengan hasil ringkas
     - Action: User bisa proceed ke dashboard
   
   - If async (>= 1000 rows):
     - Send email: "Kuesioner siap untuk di-analyze" (when done)
     - Show notification: Dashboard badge "1 new analysis"
     - Action: User refresh dashboard untuk melihat hasil

     - Field 4: Initial Prompt (textarea, optional)
     - Field 5: File Upload (optional, max 5 files)
   
2. **Form Submission**
   - User fills form & clicks "Generate Laporan"
   - Submit: POST to `/api/gjm/ai-prompt/triwulan`
   - Controller: `API/GJM/DashboardApiController@generateTrwReport()`
   - Validation:
     - periode: required, valid format
     - prodi: required, in whitelist
     - prompt: optional, max 2000 chars
     - files: optional, max 5 files, each < 50MB
   
3. **Intent Parsing (Agent)**
   - AIAgentService receives request
   - Analyze request:
     ```
     Input:
       periode: "Triwulan 1 Tahun 2026",
       prodi: "TRPL",
       prompt: "Fokus ke kualitas pembelajaran dan RPS"
     
     Parse:
       task_type: "LAPORAN_TRIWULAN"
       primary_focus: "kualitas pembelajaran"
       secondary_focus: "RPS compliance"
       filters: {
         prodi: "TRPL",
         periode: [2026-01-01, 2026-03-31]
       }
       requires_rag: true
       requires_ocr: (depends on files)
       confidence: 0.92
     ```
   
4. **File Processing (if uploaded)**
   - Check file type:
     - Images (.jpg, .png, .gif): Send to OCRService
     - Documents (.docx, .pdf): Send to TextExtractionService
     - Excel (.xlsx): Parse structured data
   
   - OCR Processing:
     - PaddleOCR extract text dari images
     - Fallback: Claude Vision (if PaddleOCR fails)
     - Store extracted text: Send to ChunkingService
   
   - Document Processing:
     - Extract all text from Word/PDF
     - Clean formatting
     - Split into sentences
     - Send to ChunkingService
   
   - Chunking & Indexing:
     - ChunkingService break text into 500-word chunks
     - EmbeddingService generate vector untuk tiap chunk
     - VectorDatabaseService store chunks + embeddings
     - Metadata: source=upload, upload_id=xxx, source_id=yyy
   
5. **Data Collection Phase**
   - AIAgentService calls `extractAndIndexKuesioneData()`
   - Queries executed:
     ```sql
     SELECT * FROM hasil_analisis_lengkap
     WHERE prodi = 'TRPL'
       AND periode = 'Q1 2026'
       AND analyzed_at > (now() - 90 days)
     LIMIT 100;
     ```
   
   - Aggregates data:
     - Kuesioner kepuasan: rata-rata 3.6/4.0
     - RPS compliance: 18/20 matakuliah (90%)
     - Materi delivery: 95% tepat waktu
     - Dosen attendance: 99% hadir
   
   - For each matakuliah in TRPL:
     - Count: Number of kuesioner responses
     - Average: Satisfaction score
     - Trend: Compare with T1 2025
   
6. **RAG Context Retrieval**
   - RAGRetrievalService executes semantic search
   - Query embedding: "Kualitas pembelajaran TRPL Triwulan 1"
   - Search in DocumentChunk table:
     ```sql
     SELECT *,
            SIMILARITY(embedding, query_vector) as score
     FROM document_chunks
     WHERE source_type IN ('laporan', 'monitoring', 'analysis')
       AND metadata->>'prodi' = 'TRPL'
       AND SIMILARITY(embedding, query_vector) >= 0.7
     ORDER BY score DESC
     LIMIT 10;
     ```
   
   - Retrieved results:
     - Chunk 1: "TRPL memiliki compliance RPS tertinggi..." (0.92)
     - Chunk 2: "Kualitas materi pembelajaran konsisten..." (0.88)
     - Chunk 3: "Dosen TRPL responsif terhadap feedback..." (0.85)
     - ... (5 more chunks)
   
   - Context assembly:

## 3.2.6.13 Advanced Patterns & Anti-Patterns

### 3.2.6.13.1 Recommended Patterns ✅

**Poin-demi-Poin:**

1. **Circuit Breaker for AI Providers**
   - **What:** Prevent repeated calls to failing service
   - **How:** After 3 consecutive failures, open circuit
   - **When closed:** Allow requests to pass through
   - **When open:** Immediately fail without calling service
   - **When half-open:** Allow 1 test request
   - **Transition:** Success → Closed, Fail → Open
   - **Benefit:** Faster failure, resource savings

2. **Cache-Aside Pattern**
   - **What:** Check cache first, compute if miss
   - **How:**
     ```
     1. Check cache for key
     2. If exists & valid → return cached
     3. If miss → compute result
     4. Store to cache with TTL
     5. Return result
     ```
   - **Benefit:** Fast reads, automatic invalidation

3. **Retry with Exponential Backoff**
   - **What:** Retry failed requests with increasing delay
   - **How:**
     ```
     Attempt 1: Wait 1 second, retry
     Attempt 2: Wait 2 seconds, retry
     Attempt 3: Wait 4 seconds, retry
     Attempt 4: Fail
     ```
   - **Benefit:** Better handle transient failures

4. **Bulkhead Pattern**
   - **What:** Isolate resources per service
   - **How:**
     - Spark jobs: Max 5 concurrent
     - AI calls: Max 10 concurrent
     - DB connections: Max 50
   - **Benefit:** Prevent cascading failures

---

### 3.2.6.13.2 Anti-Patterns to Avoid ❌

**Poin-demi-Poin:**

1. **Blocking HTTP Calls for Long Jobs**
   - ❌ What: Direct call from HTTP request to Spark job
   - ❌ Problem: HTTP timeout after 30 seconds
   - ✅ Instead: Queue job, return immediately
   - ✅ Implementation: Laravel job queue + Redis

2. **Hardcoded Thresholds**
   - ❌ What: Similarity threshold = 0.3 (in code)
   - ❌ Problem: Can't tune without redeploying
   - ✅ Instead: Move to config/rag.php
   - ✅ Allow: Dynamic adjustment via admin panel

3. **No Error Handling**
   - ❌ What: No try-catch on external API calls
   - ❌ Problem: Unhandled exceptions crash request
   - ✅ Instead: Wrap all external calls in try-catch
   - ✅ Log: All errors with context for debugging

4. **Unnecessary Re-embedding**
   - ❌ What: Generate embedding for same chunk twice
   - ❌ Problem: Wasted API calls, slow
   - ✅ Instead: Cache embeddings by content hash
   - ✅ Benefit: 10x faster on repeated chunks

5. **Single Provider Dependency**
   - ❌ What: Only use OpenAI, fail if quota exceeded
   - ❌ Problem: Service outage
   - ✅ Instead: Implement fallback chain
   - ✅ Use: 5+ providers (cost spread)

## 3.2.6.14 Debugging & Troubleshooting Guide

### 3.2.6.14.1 Common Issues & Solutions

**Poin-demi-Poin:**

1. **Issue: Laporan Generation Hangs (> 30 sec)**
   - **Likely Cause:**
     - RAG retrieval slow (large vector DB)
     - AI provider timeout
     - Database connection issue
   
   - **Debug Steps:**
     - Check logs: `storage/logs/laravel.log`
     - Monitor: DB query time (slow query log)
     - Monitor: AI API response time
   
   - **Solutions:**
     - Add vector DB index on embedding column
     - Increase AI timeout to 60 seconds
     - Upgrade DB server CPU

2. **Issue: Quality Score Always Low (< 0.7)**
   - **Likely Cause:**
     - RAG context not relevant
     - AI response not answering question
     - Prompt too vague
   
   - **Debug Steps:**
     - Check RAG chunks retrieved (similarity scores)
     - Check AI response content (relevant?)
     - Check user prompt (clear & specific?)
   
   - **Solutions:**
     - Improve chunk relevance (better chunking)
     - Refine prompt template
     - Add more training data

3. **Issue: File Upload Fails**
   - **Likely Cause:**
     - File size > 50MB limit
     - File type not in whitelist
     - Storage permission denied
   
   - **Debug Steps:**
     - Check error message (specific?)
     - Check file size & type
     - Check storage directory permissions
   
   - **Solutions:**
     - Increase file size limit
     - Add file type to whitelist
     - Fix directory permissions

4. **Issue: Cache Not Invalidating**
   - **Likely Cause:**
     - Cache key not cleared on update
     - TTL set too high
     - Wrong cache layer being cleared
   
   - **Debug Steps:**
     - Check cache keys in Redis
     - Check TTL values
     - Verify invalidation code triggered
   
   - **Solutions:**
     - Call Cache::forget() after update
     - Reduce TTL for frequently-changing data
     - Use cache tags for bulk invalidation
